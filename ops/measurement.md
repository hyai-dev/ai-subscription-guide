# 来源标记与转化测量范围

本仓库使用 `utm_source=github`、`utm_medium=referral`，并将主题和站点编码进 `utm_campaign`。完整链接由 [清单](../data/tracking-links.json)生成。两站当前自建归因白名单保留这三个字段；不依赖会被清洗的 `utm_content`。

## 当前已经做的

- 建立稳定的文章 ID、主题、站点、目标 URL 和 campaign 对照。
- 对相关落地页做匿名 GET 检查，确认公开可达；这不代表追踪事件已收集。
- 区分自有 GitHub 发布和独立媒体推荐，不把自己的归档数当外部推荐数。

## 当前还没有证明的

两站源码中存在归因、同意控制及部分客户端埋点，但标准直达结账链路尚未证明将来源完整传到已确认付款/交付订单。表单里的嵌套 attribution 与后端读取字段也需要统一验收。因此不能计算或展示“GitHub 带来多少实付订单”，不能把前端成功事件当财务确认。

本轮只改公开指南，不修改商业站的结账、支付回调或真实订单。详细只读发现见 [源码与公开请求审计](measurement-audit-20261019.json)。没有真实订单、秘密或客户信息。

## 后续验收口径

| 阶段 | 需要的证据 | 不能替代它的证据 |
| --- | --- | --- |
| 教程访问 | 经同意的有效 page view 与时间窗/去重规则 | 链接里有 UTM |
| 商品点击 | 具体 topic/site 的实际点击事件 | README 链接出现次数 |
| 创建订单 | 服务端订单 ID 与来源字段 | 客户端点击下单 |
| 付款确认 | 原支付渠道核验的订单状态，按订单去重 | 支付按钮点击或跳转成功 |
| 交付 | 服务端交付状态与对应订单 | 卡密展示示意图 |

先建立数据收集与去重基线，完成受控的实际链路验收后，再计算阶段转化率和内容贡献。没有真实验收就保留待办，不生成示例经营数字。
